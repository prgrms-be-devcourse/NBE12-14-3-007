# Kotlin 마이그레이션 2단계 계획: 테스트를 먼저 Kotlin스럽게, 코드는 그 테스트에 맞춰

## 한 줄 요약

**스냅샷을 기준 답안으로 삼아 Kotlin 테스트를 먼저, 아주 Kotlin스럽게 쓴다.
그다음 그 Kotlin 테스트를 통과하도록 Kotlin 코드를 새로, 예쁘게 작성한다.**

## 흐름

```
스냅샷 (기준 답안)
   │  "이 요청엔 이렇게 답해야 한다"
   ▼
Kotlin 테스트 작성  ── 목표로 하는 Kotlin다운 모양으로, 새 패키지에
   │  "코드가 이런 모양이면 좋겠다" (설계도 역할)
   ▼
Kotlin 코드 작성  ── 위 테스트를 통과시키도록
   ▼
검증: Kotlin 테스트 통과 + 스냅샷 다시 찍어 비교 (실제 차이 0개)
```

| 역할 | 무엇이 맡나 |
|---|---|
| **기준 답안** | 스냅샷(`snapshots/baseline/`)과 기존 Java 테스트 |
| **설계도** | 새로 쓴 Kotlin 테스트 (코드가 어떤 모양이어야 하는지 보여 줌) |
| **구현** | 테스트를 통과시키는 Kotlin 코드 |

---

## 1. 지금까지 한 것 (1단계)

| 한 일 | 결과 |
|---|---|
| Java 코드를 Kotlin으로 1:1 변환 | Kotlin 81개 / Java 92개 (`dev` 기준). 동작은 그대로 |
| 테스트는 Java 그대로 | 테스트 360개가 변환 때마다 통과 → 동작이 같다는 안전망 |
| **스냅샷 기준선 만듦** | API 응답 44개를 파일로 저장 (`snapshots/`). Java 시절과 지금을 비교했더니 실제 응답은 모두 동일 |

## 2. 왜 이 순서인가

1단계 코드가 Kotlin스럽지 못한 이유는 **Java 테스트와 호출부가 지금의 코드 모양을 정해 놓았기 때문**이다.
(수동 빌더, `protected set`, `likeCount()` 같은 접근자 등)

그래서 순서를 뒤집는다.
- 테스트가 **코드 모양을 정한다.** 테스트에서 `Inquiry(title = "...")`, `result.likeCount`처럼 쓰고 싶은 모양을 먼저 적는다.
- 코드는 **그 테스트를 통과시키는 방향으로** 새로 쓴다. 기존 코드 모양에 끌려가지 않는다.
- 동작이 바뀌지 않았다는 증거는 **스냅샷**과 **Java 테스트의 기대값**이 준다.

## 3. 진행 방식

1. **진행사항을 전부 "시작 전"으로 바꾼다.** (2단계 기준. 1단계 결과인 Kotlin 코드와 스냅샷은 그대로 둔다)
2. **스냅샷과 Java 테스트를 기준으로 Kotlin 테스트를 먼저 쓴다.** 목표로 하는 Kotlin다운 모양으로 쓴다.
3. **Java 테스트는 지우지 않고 남겨 둔다.** (기준이 되는 원본)
4. **Kotlin 테스트는 새 패키지에 쓴다.** (Java 테스트와 이름이 겹치지 않게)
5. **Kotlin 테스트가 정해진 뒤, 그 테스트를 통과시키도록 Kotlin 코드를 작성한다.**
6. **Kotlin 테스트는 스냅샷·Java 테스트와 입력과 기대값이 같아야 한다.** (아래 기준)

## 4. "똑같다"의 기준

"비슷하게"가 아니라 아래처럼 정해서 확인한다.

| 항목 | 기준 |
|---|---|
| 테스트 개수 | Java 테스트와 **1:1** (메서드 326개, 실행 케이스 360개). 같은 이름으로 짝을 맞춘다 |
| 입력(준비 데이터) | **같다** |
| 기대값(상태 코드, 응답 값, 예외, 호출 여부) | **같다.** API 테스트는 스냅샷의 응답이 곧 기대값 |
| 객체를 만드는 방식, 코드 모양 | **달라도 된다 (Kotlin스럽게)** |
| 마지막 API 응답 | 스냅샷으로 비교해서 **실제 차이 0개** |

## 5. 같은 동작임을 확인하는 방법

| 방법 | 확인하는 것 |
|---|---|
| **스냅샷 비교** (`snapshots/USAGE.md`) | 새 코드를 만든 뒤에도 API 응답이 그대로인지 |
| **Kotlin 테스트와 Java 테스트의 기대값 대조** | 매핑표(Java 메서드 ↔ Kotlin 메서드)로 빠진 테스트가 없는지, 기대값이 같은지 |
| **(선택) 일부러 버그를 넣어 보기** | Java 테스트가 실패하는 곳에서 Kotlin 테스트도 같이 실패하는지. Kotlin 테스트가 Java만큼 엄격하다는 증거 |

스냅샷은 API 응답만 비교한다. 서비스·저장소 테스트(Mockito, DB)는 Java 테스트의 기대값 대조와 "버그 넣어 보기"로 확인한다.

## 6. 진행 순서 (제안)

도메인 하나씩, **테스트 → 코드**를 한 묶음으로 끝낸다.

| 순서 | 내용 | 상태 |
|---|---|---|
| 0 | 준비: 보드 정리, 기준 태그(`java-oracle`) 만들기, AGENTS.md 반영, Kotlin 테스트 패키지 정하기 | 시작 전 |
| 1 | **시범 도메인 하나 선택** (예: `weather`처럼 작고 다른 곳이 참조하지 않는 것). 테스트 → 코드 → 스냅샷 비교까지 한 번 끝까지 해서 방식 확정 | 시작 전 |
| 2 | 나머지 도메인 반복 (의존이 적은 것부터, `member`·`festival`·`BusinessException` 같은 많이 참조되는 것은 마지막) | 시작 전 |
| 3 | 스냅샷 범위 넓히기 (로그인, 회원, 행사, 댓글, 커뮤니티, 좋아요 추가) | 시작 전 |
| 4 | 정리: 옛 모양 호환 코드와 Java 테스트 정리 | 시작 전 |

**API 계약 테스트(159개)** 는 HTTP 요청과 응답만 보는 테스트라서 코드 모양과 상관이 없다.
→ 기준 답안(스냅샷)과 가장 직접 이어지고, 코드를 새로 써도 그대로 통과해야 하므로 **가장 먼저 Kotlin으로 옮기기 좋다.**

## 7. 미리 정해 둘 것

1. **테스트가 아직 없는 코드 모양을 부르면 컴파일이 안 된다.**
   Kotlin 테스트를 목표 모양으로 먼저 쓰면 코드가 완성될 때까지 컴파일이 깨진 상태가 된다. 테스트 소스는 한꺼번에 컴파일되어서, 이 상태가 길어지면 팀 전체의 테스트가 막힌다.
   → **도메인 하나씩 테스트와 코드를 같은 브랜치에서 끝내고, 초록(전부 통과)일 때만 머지한다.**
2. **새 코드를 어디에 둘 것인가.** 기존 위치를 교체할지(그때 Java 테스트가 깨지므로 4번 참고), 새 패키지에 병행할지 정한다.
3. **Java 테스트를 남겨 두면 기존 코드 모양을 바꿀 때 컴파일이 깨진다.**
   → 방법 A: 옛 모양(`builder()` 등)을 `@Deprecated`로 한동안 남긴다 / 방법 B: Java 테스트를 기준 태그로 보관하고 컴파일 대상에서 제외한다. **B를 기본으로, 필요한 곳만 A를 추천.**
4. **패키지 이름.** 예: `src/test/kotlin/com/team007/room_escape/` 아래 새 패키지. 이름을 정한다.
5. **실행 시간.** 테스트가 두 벌이 되어 시간이 늘어난다. CI에서 어떻게 돌릴지 정한다.
6. **AGENTS.md / CLAUDE.md의 "`src/test` 수정 금지"** 문구를 2단계 규칙에 맞게 고친다.

## 8. 한계

- 스냅샷은 지금 44개 요청(문의, 후기, 날씨, 오류 응답, 문서)만 담고 있다. 로그인, 회원, 행사, 댓글, 커뮤니티, 좋아요는 아직 없다. 이 범위를 넓히기 전에는 그 도메인의 "기준 답안"이 약하다.
- 기상청 실제 응답, 메일 본문, 스케줄러 같은 부수 효과는 어느 방법으로도 확인하기 어렵다.
